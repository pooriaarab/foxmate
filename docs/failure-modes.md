# Failure modes

foxmate composes the fox primitives. Each primitive has its own failure
modes and tests. Bugs in foxmate hide in the wiring between them: an
approval that shows one action and runs another, a run that reaches a
cloud model, page text that reaches the planner without foxshield, a lent
tab that loses its guard, or a memory that injects text from a web page.

We write each failure mode here first. Then we write its test, then the code.
An E2E check in real Firefox is the first choice. A test in `tests/` covers a
failure that an E2E check cannot reach, or reaches only slowly.

## Brain: which model plans (`src/brain.ts`)

The brain turns the user's settings into a foxmind `Mind`. foxmate uses only
models on this computer or in Firefox. It has no cloud planner, so a run must
never reach a cloud model.

## Workflow cache: replay a plan that worked (`src/workflow.ts`, `src/agent.ts`)

After a run ends done, foxmate keeps its successful calls for the tab's origin
and the exact goal with its memory notes. The next run of the same goal on the
same origin replays them with no model call, up to the end: the planner writes
the finish. A goal of the same shape, the same task with other values, replays
them too, with its own values (WF12-WF21). Each call still goes through the
gate, and every approval is asked again.

|---|---|---|---|
| WF1 | A replayed click lands on another control, because control ids changed | A click or an act is kept as the control's role, label and submit flag. At replay, foxmate finds the one control in the newest snapshot with the same three; none, or more than one, ends the replay. | `tests/workflow.test.ts` WF1 |
| WF2 | The replay goes on after a step failed or the page changed, on a plan that no longer fits | A failed result, a skipped call or a failed check ends the replay. The planner takes over with the history so far. | `tests/workflow.test.ts` WF2; `tests/agent.test.ts` WF2 |
| WF3 | A replayed step skips the gate or an approval | A replayed call is a planner reply like any other: foxloop checks it with the gate, and each approval is asked. | `tests/agent.test.ts` WF3 |
| WF4 | The user's answer to a question is replayed, though the user may answer otherwise this time | A question is asked again. When the answer differs from the kept one, the replay ends. | `tests/agent.test.ts` WF4 |

## Shield: page text before the planner (`src/shield.ts`)

Every page text that foxloop's browser tools read goes through foxshield
first. The planner gets `sanitize()` output, not raw DOM text. The page is
untrusted data.

| S3 | The scan throws in the tab (a frame went away, the page navigated) | foxmate withholds the page text and says so. Raw text never goes to the planner. | `tests/shield.test.ts` S3 |

## Recall: memories in the goal (`src/recall.ts`)

foxmate recalls memories that fit the goal and adds them to the goal as
notes. The goal is trusted text, so a note must come from the user.

| # | Failure mode | Wanted behaviour | Test |
|---|---|---|---|
| M1 | A memory that a page or an import wrote (`source` is not `user`) | It is never a note. | `tests/recall.test.ts` M1 |
| M2 | A note holds markup such as `</untrusted-data>` or `<\|im_start\|>` | foxmate removes `<` and `>` from notes. | `tests/recall.test.ts` M2 |
| M3 | The embedder fails (the model is not loaded) | The run goes on with no notes. The result says why. | `tests/recall.test.ts` M3 |
| M4 | A memory that does not fit the goal | Memories under the minimum similarity stay out. | `tests/recall.test.ts` M4 |
| M5 | A very long memory, or many memories | Each note is cut to 300 characters. At most 5 notes. | `tests/recall.test.ts` M5 |
| M6 | A note holds zero-width or bidi characters that hide text | foxmate removes them. | `tests/recall.test.ts` M6 |

## Approvals: one answer per exact action (`src/approvals.ts`)

The sidebar and, when it is on, the phone can both answer an approval. The
answer must reach the one request it names, once.

| # | Failure mode | Wanted behaviour | Test |
|---|---|---|---|
| A1 | An answer names another request | It does not decide any other request. | `tests/approvals.test.ts` A1 |
| A2 | Two channels answer (the sidebar approves, then the phone denies) | The first answer decides. The second one is ignored and reported as late. | `tests/approvals.test.ts` A2 |
| A3 | An answer comes before foxloop asks (a fast click) | It is kept for that request only, if foxgate holds the request. | `tests/approvals.test.ts` A3 |
| A4 | Nobody answers | The request ends as no at its foxgate expiry. The run does not hang. | `tests/approvals.test.ts` A4 |
| A5 | The run ends while a request waits | Every waiting request ends as no. | `tests/approvals.test.ts` A5 |
| A6 | An answer is lost, so the trail cannot show who approved | Each deciding answer goes to the trail with the request id, the decision and the channel. | `tests/approvals.test.ts` A6 |
| A7 | An answer comes after its run ended (the phone prompt stayed open), and foxgate reuses the still-pending request for the same action in the next run, so the old answer approves it | Only requests that the current run announced can be answered. When a run ends, foxmate rejects its open requests in foxgate. | `tests/approvals.test.ts` A7 |

| # | Failure mode | Wanted behaviour | Test |

## Bench over MCP (`cli/bench-mcp.mjs`)

`foxmate bench-mcp` is an MCP server on stdio for `foxbench run --agent mcp`.
Its one tool, `run_task` {url, goal}, runs one task with the foxmate bench
adapter (BN1-BN7), so every foxbench benchmark can score foxmate without
foxbench importing foxmate.

| # | Failure mode | Wanted behaviour | Test |
|---|---|---|---|
| BM1 | The server writes a line that is not MCP to stdout (a progress line, a tunnel note), so foxbench's client cannot read the reply and every task is an adapter error | stdout carries MCP messages only. Every console line of the server goes to stderr. | e2e `bench-mcp` |
| BM2 | `run_task` gets no url or no goal, or a url that is not http(s), and the run opens a blank tab and reports a failed task as if foxmate had tried | The reply is an MCP tool error (foxbench counts an adapter error), and no tab opens. | e2e `bench-mcp` |
| BM3 | Firefox, Ichabod or a model tunnel does not start, and the tool reply says done false, so a broken setup scores as foxmate failing every task | The reply is a tool error with the cause, so foxbench counts adapter errors. The next call tries to start Firefox again. | e2e `bench-mcp` |
| BM4 | A tool reply or error holds `ICHABOD_API_KEY`, a model gate path or the tunnel host, and foxbench writes it to the score log | The key, each gate path and the tunnel host are taken out of every reply and error text. | e2e `bench-mcp` (Ichabod) |
| BM5 | Two calls come at once and share one tab and one sidebar, so one run reads the other's end | Calls run one at a time, in order, in the one Firefox. | e2e `bench-mcp` |
| BM6 | A benchmark scores the answer (BrowseComp, AssistantBench), and the reply holds only done, so every answer scores wrong | A done run returns its finish summary as `answer`. | e2e `bench-mcp` |
| BM7 | foxbench stops the server at a task's time limit (SIGTERM to its process tree), and the Ichabod session or the tunnel stays open | On SIGTERM, SIGINT or a closed stdin, the server closes Firefox and the model gates, then exits. A close that waits on a lost session (seen: a server whose foxbench died hung for minutes) does not hold the exit past 10 s. | e2e `bench-mcp` (Ichabod) |
| BM8 | The noop agent and foxmate get the same score on the train suite, so the E2E test cannot tell a server that works from one that does not | The E2E test runs foxbench's train suite twice: noop scores 0, and foxmate through `bench-mcp` scores above 0 with no adapter error but a time limit (foxbench counts a task over its time limit as one). | e2e `bench-mcp` |
